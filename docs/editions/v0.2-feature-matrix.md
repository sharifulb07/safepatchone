# SafePatch v0.2 edition entitlement matrix

Target software release: **0.2.0**, shared by Community, Developer, Team, Business
and Enterprise. This milestone publishes entitlement and limit configuration;
it does not create another release stream, engine, schema or application.

The executable configuration is
[`internal/config/editions_v02.json`](../../internal/config/editions_v02.json).
`config.V02Editions(FeatureCatalog)` returns validated, independent copies.
Migration `000006_v02_edition_matrix.up.sql` seeds identical configuration, checked
by Go/SQL parity tests. Existing sealed bundles, customer policies, quota accounting
and evidence remain unchanged. The [v0.1 matrix](v0.1-feature-matrix.md) remains a
historical release record.

with runtime composition still required. **FUTURE** means the complete product
workflow is unavailable even when the bundle records ownership. Neither status
implies a hosted service, production approval or live dependency validation.

`feat_0041` (`policy.local.advanced`). Existing capability keys are reused for all
other requested rows. No edition tokens appear in new capability keys.

Each new bundle preserves its prior mappings and inherits the new lower-tier local
grants. This retains historical forward-looking grants such as replay and proof
planning as FUTURE metadata; these totals are not implemented-feature counts.
Feature `configuration_json` records the target release and `SDK`/`FUTURE`
availability. Enterprise audit/self-host configuration additionally limits the

metadata and old bundle mappings are not rewritten.

The target release is separate from the commercial bundle ID. Applications pin
an explicit bundle version; they must not select “latest” by edition name.
The current offline CLI remains pinned to its published `community-2026-v2`
defaults. Merely loading this matrix does not switch that provider, migrate an
organization or make a FUTURE feature executable. Applying v0.2 to a deployment
is an explicit provisioning/composition action.

## Provisional limit configuration

No numeric commercial allowances were supplied. These starter profiles are
explicitly marked **PROVISIONAL**, are reviewable configuration and are not pricing
or service commitments. They are not automatically assigned to any organization.
Different approved allowances require a new immutable bundle revision. Local
execution still obeys independent Runner resource safety bounds.

Every profile specifies all eight existing limit keys. Numeric cells are INTEGER;
DISABLED is explicit, never a sentinel number for unlimited. The shared limit model
also supports UNLIMITED, but these provisional profiles do not use it.

## Enforcement and persistence

`edition_limits` stores immutable per-version templates, with foreign keys to the
existing edition and resource registries. It follows the same assemble-then-seal
lifecycle as edition feature mappings. Sealed versions cannot be extended; updates,
deletes and truncation are rejected. Historical versions have no inferred profile.
`entitlement_limits` continues to hold effective organization policy. The migration
does not modify it or customer quota usage/reservations.

Trusted provisioning must explicitly choose the bundle, retain its identity, resolve
organization ownership and publish effective feature/limit policy through existing
services. Applying a template is not an atomic cross-service provisioning API in
this milestone. Missing effective limits retain the existing fail-closed behavior.

Runtime boundaries require `EntitlementService.Has`, independent
`PermissionService.Allowed`, effective quotas and implementation readiness.
`configuration_json` is inert configuration; `Has` alone does not enforce release
availability or a foundation scope. No caller may route a future full Enterprise
operation merely because a forward-looking grant exists. Policy evaluation stays
independent of management grants: downgrades must not turn off required policies.

Tests cover exact allocations, Business/Team limits, Go/SQL parity, immutable
configuration, all five editions through the real entitlement resolver and
permission service, tenant isolation, downgrade/upgrade accounting and unchanged
policy evaluation. Native PostgreSQL assertions additionally cover immutable
templates, invalid states/keys, unchanged historical data and migration replay;
they require the existing opt-in PostgreSQL environment.

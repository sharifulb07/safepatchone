# SafePatch v0.1 edition capability matrix

Release version: **0.1.0**. Release scope: **developer preview / shared Go foundation**.
See the [release notes and validation results](../releases/v0.1.md).

| Permanent edition | Software version | Source, engine, schema and migration history |

| Community | 0.1.0 | Shared |
| Developer | 0.1.0 | Shared |
| Team | 0.1.0 | Shared |

| Enterprise | 0.1.0 | Shared |

These five identities already exist in `internal/domain/edition` and the shared
SQL migration history. They are commercial metadata, not applications or build
targets. A single build contains the same Go implementation for every edition.
Edition changes do not select another release, engine, schema or migration chain.
No stable/LTS support commitment is introduced by v0.1.

## Reading this matrix

- **SDK**: implemented shared Go code, available to admitted application callers
  with the required configuration. It is **not** an enabled end-to-end CLI or
  hosted product workflow, a plan grant, or a claim of live dependency validation.
- **FUTURE**: the product capability is not implemented for v0.1. It is **not
  enabled in this release matrix**, even if a historical entitlement bundle
  contains a forward-looking grant. There is no delivery date or commercial
  availability promise.

The three SDK rows below describe implementation availability shared by all five
editions. Actual access still requires the organization's effective entitlement,
independent actor permission, configured limits and policy. A row does not grant
anything. The later-capability table contains only FUTURE placeholders.

The executable CLI currently supports help, `entitlement show`,
`entitlement explain <feature>`, `edition`, and `whoami`, including JSON output.
It runs in the offline Community context without an account. Paid identity,
subscription and license composition are not wired into the CLI; selecting or
logging into a paid edition is not a v0.1 command. `safepatch verify` still returns
`NOT_IMPLEMENTED`, never a successful verification.

## Implemented capability scope

| Capability key | Community | Developer | Team | Business | Enterprise | Exact v0.1 scope |
| --- | --- | --- | --- | --- | --- | --- |
| `verify.basic` | SDK | SDK | SDK | SDK | SDK | Go build, test, race, vet, fuzz and benchmark adapter; go.mod, go.work and multi-module discovery; shared Runner and normalized evidence |
| `verify.security` | SDK | SDK | SDK | SDK | SDK | Configured Staticcheck, Govulncheck, Gitleaks, Semgrep, Trivy and OSV-Scanner adapters; Syft inventory adapter; upstream engines remain external prerequisites |
| `evidence.local` | SDK | SDK | SDK | SDK | SDK | Normalized records and immutable scoped local storage of exact scanner stdout/stderr and manifests; no evidence-browser/export CLI |

Fuzz additionally needs admitted `fuzz_seconds_monthly` usage; a basic grant does
not bypass quota policy. Syft success means inventory generation, not a clean
vulnerability verdict. Local execution on untrusted inputs requires the container
Runner. Hosted execution must use authoritative server/worker admission; local
Community grants are never a fallback for a hosted tenant.

Community's compiled `community-2026-v2` bundle grants `verify.basic`,
`verify.security` and `evidence.local`, alongside the historical forward-looking
`intent.basic` and `graph.local` grants. The latter two remain **FUTURE** below.
Other pinned bundles are not automatically upgraded to Community v2 or assigned
its local-evidence grant. Shared SDK availability is distinct from those immutable
commercial allocations.

## Shared foundation shipped as code

All editions use the implemented domain catalog and edition types, entitlement
resolver/snapshot/provider contracts, independent permission service, API/CLI/
worker enforcement helpers, quota accounting, secure Runner adapters, Verifier
SDK and evidence contracts. These are shared infrastructure, not additional
premium product promises. Persistence and runtime composition gaps are listed
in the release notes.

`FUTURE` is the release matrix's availability status. It does not add a database
enum or rewrite the catalog's existing `PLANNED` registration metadata. Existing
CLI entitlement output reports grant ownership and that catalog status separately;
an `enabled` grant is not an implementation claim. This matrix deliberately does
not turn seed grant counts into lists of available product features.

Published bundles, existing customers' grants, evidence and quota data remain
unchanged. Any later capability activation must have a real implementation,
authoritative access checks, entitlement/authorization boundary tests and tests
showing that grant changes preserve data before its release status changes.
